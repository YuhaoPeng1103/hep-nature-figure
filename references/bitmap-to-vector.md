## 0. 一句话

**几何只来自第 ② 步的临摹层。** 第 ③ 步只做三件事：按元素**拟合**、按声明**补全**、把线稿**贴回**。
第 ④ 步再叠一层不可见的「每个物理结构一条闭合路径」，让**点一下 = 一个物理结构**。

```
① 位图（客户选定，唯一权威的外观）
      ↓  raster_to_vector_semantic.py
② 临摹（逐像素 + 语义图层：每个物理元素一个 <g data-element="...">）
      ↓  trace_rebuild.py（对象档）/ 逐行渐变网格（光滑档）
③ 重建（每个元素 = clipPath + 真渐变 + 线稿贴回）
      ↓  pick_layer.py（+ amodal 补全产出的 _sil.json）
④ 拾取层（每结构一条 fill-opacity="0" pointer-events="all" 的闭合路径）
```

## 1. 四档：什么时候用哪个

| 档 | 做什么 | 产物 | 什么时候用 | 验收 |
|---|---|---|---|---|
| **① 位图** | 生图模型出图、客户选定 | `gen/chosen.png` | 总是 | 闸口②（物理对） |
| **② 临摹** | 逐像素 + 语义分层 | `<stem>_trace.svg` | **总是**（③ 的几何只能从这里来） | 回渲染 MAE |
| **③-A 对象档** | 把每个元素重做成「可改形状/改色」 | `<stem>_obj.svg`（几百条 path） | 客户要改几何 / 配色时 | **逐元素**看，不看整幅 MAE |
| **③-B 光滑档** | 逐行自适应渐变网格（`shade_smooth.py`） | `<stem>_mesh.svg`（几万条 path） | **默认交付**：放大不糊 | `smooth_metric.py` |
| **④ 拾取层** | 每结构一条不可见闭合路径 | `<stem>_mesh_pick.svg` | 要「点一下 = 一个物理结构」 | `pick_verify.py` |

> ★ **③-A 与 ③-B 是两个档，不是同一个文件**：`_mesh.svg` 保真 + 光滑但难改形状；
> `_obj.svg` 能改形状但天生不平滑。**两个都交**，说明书里写清哪个干什么。

## 2. ② 临摹：几何的唯一来源（为什么不能重新抠）

老路是「颜色谓词 ∩ 包围盒」，实测的两种翻车：

| 现象 | 根因 |
|---|---|
| `a-nucleus-far` 的底边被**切平** | 手写的框 `(575,35,810,255)` 比真 bbox `(586,46,800,306)` 矮，底边被裁掉 |
| 「板下淡出」成了一条**卷曲细带** | 那片区域不是单连通的，`findContours` 在非单连通掩膜上描出来就是一条飘带 |

改成**只从 `<g data-element>` 的掩膜取几何**之后，三个体积的 MAE：

| 版本 | 几何来源 | MAE |
|---|---|---|
| v35 | 颜色阈值 | 2.49 |
| v37 | 颜色阈值 ∩ 包围盒 | 5.28 |
| **v38** | **`<g data-element>` 掩膜** | **1.95** |

**回归自检基线**：`trace_rebuild.py` 在 v38 的输入上重跑，三个体积的像素数
**30044 / 25884 / 28268** 应逐一复现，整图 **MAE = 1.946**。换代码先跑这条。

### 产物规格（③ 只认这个）

- 每个物理元素包在**一个带 `id` 的 `<g>`** 里，`data-element="<物理名>"`；
- `<g>` 内部的形状是 `RECT` 式**碎矩形** path（`M..h..v..h-z`）—— 这是 `raster_to_vector_semantic.py` 的输出格式；
- 一个元素内部可以有**很多条**碎矩形（一个元素几百条是正常的）。

## 2.5 ② 的「语义层」从哪来：IR 引导的可见像素物理轮廓（v4.16，`ir_contour_seg.py`）

作者 2026-10-15：「我现在需要的就是**在可见像素的物理轮廓上分割**，你可以配合 IR 使物理轮廓
分割更正确啊。AmodalSVG 走的就是这条：**VLM 引导 + grounded segmentation + inpaint 补全** ——
它也没指望分割器自己给出『完整物理物体』。」

所以本步的职责边界（= AmodalSVG 的第一、二步）：

- **语义**由 IR 给（哪个元素是什么、叠放序 `z`、谁遮谁 `composition.穿透/遮挡`、
  形态族 `primitive`、数量 `×N`、位置「上核/下核」）；
- **边界**只落在**可见像素**上，不猜被完全遮住的部分；
- 被切掉的那部分**不给假轮廓**，只出读数（看到多少 / 缺多少），交给 §6 的 amodal 补全。

```bash
python tools/ir_contour_seg.py --bitmap <位图.png> --ir <IR.yaml> --outdir <dir>
#   -> labels.png（一物一层）/ overlay.png（压在原图上）/ report.json（读数）
```

### 为什么不是「16 色调色板 + 同色连通」（现有路线）

实测同一张位图（`fig_upc_v415/render/pick/cand_s4192.png`，2324x1268），两种切法的读数：

| 物理元素 | 现有路线（`segsem.quantize` 16 色）：切成几个颜色类 | 最大那类只占 | 本工具 |
|---|---|---|---|
| 反应平面 S1 | **11** | 11.7% | 1 层，4 角平行四边形 |
| 核 A / 核 B | 各 **6** | 20.9% / 21.9% | 各 1 层（球团整体剪影） |
| 平面 S1 ∩ 核 | 颜色类 `#18172c` 同时承载 **S1 + N1 + N2** | — | 各自独立 |
| 颜色类 `#49424c` | 同时承载 **N1 + N2 + A1** | — | — |

一句话：**现有路线切的是颜色类，不是物理轮廓** —— 一个物理物体被切成十来个类，
一个类里又塞进好几个物理物体。图上看就是「板面被切成一片碎多边形网、每个核子球各成一类」。

### IR 里真正用得上的四样先验（都在 `elements[]` / `composition` 里现成写着）

1. `elements[].z` —— 叠放序（大 = 靠前先占）。**边界因此落在「前面那个物体的轮廓」上**，
   而不是落在「颜色变化」处。实测：橙色一大块 = 光子线 G1 + 顶点 V1 + 末态箭头 P1，
   按 z 序 8→7→6 从前到后剥，三样各自成层。
2. `elements[].primitive` —— 形态族。**同色必须靠厚度/亮度切开**：末态箭头半宽最大 51.1 px、
   波浪线最大 13.4 px（取 blob 最大半宽的 0.45 当门限才切得开；固定 7 会把 96% 判成箭头）。
3. `elements[].material` —— 声明配色。**只当仲裁与读数，不当主判据**（见下「配色会失效」）。
4. `composition.穿透 / 遮挡` —— 谁压谁、被压的那半还看不看得见。

### ★ 实测教训一：配色先验会失效，主判据必须是形态+数量+位置

同一张位图上，IR 声明的颜色与位图实际差多少（LabΔ，阈值 26）：

| 元素 | IR 声明 | 实测 LabΔ | 结果 |
|---|---|---|---|
| N1 核 A | `#a9bcf3 → #38489f` | **57.1** | 位图把它画成「红球 + 蓝灰球」的球团 |
| N2 核 B | `#f6b39c → #a8342a` | **49.5** | 同上 |
| A1 速度箭头 | `#2b2f38` | **52.1** | 位图画成一红一蓝 |
| G1 光子线 | `#f0a63c` | 41.7 | 有明暗过渡，只有高光命中 |
| S1 板面 / B1 标注 / V1 顶点 | — | 14.2 / 18.5 / 19.5 | 一致，可用 |

**结论**：「配色命中」这一列本身就是一条交付读数 —— 它同时在说「生成模型有没有听 IR 的话」。
配色对不上时，按配色找元素会全盘找错（实测第一版把左核当成了坐标三轴）。

### ★ 实测教训二：读数是拿来**发现位图与 IR 不一致**的，不是拿来硬套 IR 的

同一张位图，本工具量出来的四条（都是位图自身的物理问题，不是分割问题）：

| 项 | IR 声明 | 位图实测 | 说明 |
|---|---|---|---|
| HP3 核的压扁比 | 高/宽 2.2:1 | bbox 1.11 / 1.15，主轴比 1.21 / 1.23 | **两个核都接近球形，不是 Lorentz 压扁的高瘦扁球** |
| HP5 末态对背对背 | 夹角 > 90°（理想 120°） | **约 63°~75°** | 两支末态箭头张口不够，点积 > 0 |
| 「板把核切一半」 | `穿透`：前后各露一半 | 可见剪影完整（凸包差额只有 21 px 厚 = 球团毛边） | 位图把板画在核**后面**，压根没切 |
| z 序 | P1(8) > V1(7) > G1(6) | 剥得开 | ✓ |

★ 判「真被切掉一整块」不能用「凸包差额」—— 球团的外轮廓本来就是毛边，凸包差额天生有 ~20%。
要用**缺口的最大内切半径**和物体等效半径比（> 0.35 才算被切掉一整块）。实测两核都是 21 px 厚 → 只是毛边。

### ★ 实测三：SAM 切的是「视觉块」，不是物理轮廓（2026-10-15，`scripts/sam_probe.py`）

作者问：「为什么不采用语义分割，你试过吗？」「现在的分割不是分割物理轮廓？SAM 是分割物理轮廓的？」

**先承认一件事**：2026-10-15 之前，这个环境里连 `torch` 都没有，全工作区 400+ 条出图记录里
**没有一次真的调过 SAM** —— 所以「不用 SAM」在此之前一直只是**设计选择**，不是实测结论。
本轮手装了 torch 2.5.1+cpu / torchvision 0.20.1 / timm 0.9.16 / MobileSAM（装法写在
`scripts/sam_probe.py` 文件头；本机 `pip` 的 TLS 是坏的，装包必须 urllib 下 wheel 再本地装），
在**同一张** UPC 位图（`fig_upc_v415/render/pick/cand_s4192.png`，2324x1268；SAM 输入长边 1024）
上跑了 MobileSAM vit_t 的 `SamAutomaticMaskGenerator`：

| 读数 | 默认档（pIoU .88 / stab .95）104 块 | 宽松档（pIoU .80 / stab .90 / pps 48）250 块 |
|---|---|---|
| 块覆盖画布 | 15.3% | 62.9% |
| **反应平面 S1**（占画布 20.3%，最大的物理元素） | 最大块只覆盖板面 **1%**；板面 **98%** 的像素没有任何块覆盖 | 最大块 8%（26 块才拼到 16%）；板面 **84%** 没被覆盖 |
| 核 N2（左下球团，配色统一） | 最大块 **88%** | 87% |
| 核 N1（右上球团，灰/红杂色球混在一起） | 最大块 **1%**，要 **37 块**才拼到 30% | **90%** |
| 末态箭头 P1 / 三轴 T1 / 顶点 V1 | 45% / 32% / 62% | 81% / 92% / 89% |
| **IR 引导（§2.5 本工具）** | **10/10 元素，各 1 层** | 同左 |

（另跑了一组更稀的网格 pps=16 复核：N2 88% / N1 1% / S1 1%，结论不随点数变。）

三条结论（全部是在这张图上量出来的，不是印象）：

1. **SAM 的判据是「像素视觉一致性 + 边界」，它没有物理身份这个概念。** 它抓住左下球团，
   是因为那块球团配色统一；抓不住右上球团，是因为同一堆球里混了两种颜色 ——
   **两个核在物理上完全同类，SAM 一个抓到一个抓不到**（换一张候选位图 `render/render_s4193.png` 结论同样成立）。
   它也没有「板」这个概念：板与背景对比度低，于是「最大的那块 mask」直接变成「整个背景 + 一小条板面」
   （宽松档 40% 画布），而真正的板面留成大片红。
2. **同一张图换一组阈值，结果不可复现**：N1 的最大块 **1% → 90%**。
   任何靠 SAM 交 `data-element` 的流程，换机器 / 换参数就变；IR 引导那条是**声明驱动**的，
   同样的输入永远给同样的 10 层。
3. **它不给「该有几个物体」**：默认 104 块、宽松 250 块，这两个数字都不来自物理。
   「两个速度箭头各一个、末态对两个、三轴图标一组」这种话只能在 IR 里写死。

⇒ 要在**可见像素**上切**物理轮廓**，靠的不是分割器选得好，而是**先声明、再分割**。
这正是 AmodalSVG 的分工（VLM 给语义 + grounded segmentation 给掩膜 + inpaint 补全），
本 skill 的对应关系是：**① IR 给语义**（比 VLM 硬 —— 可审计、可复现）·
**② `ir_contour_seg.py` 给可见像素轮廓** · **③ §6 声明式补全**。
**SAM 在这个流程里的位置**：不是主判据，而是**边界细化提议器** —— 在 IR 已经定好
「这一层属于板 / 属于哪个核」之后，用 SAM 的块边界去修这一层的边。
`scripts/sam_probe.py` 会把块存成 `masks.npz` + 对账 `report.json`，接这一步不用重跑模型。

## 2.6 ② 的两级引擎 + SAM 点提示（v4.18，实测读数）

`scripts/ir_contour_seg.py` v4.18 加了两个引擎、一次仲裁、一次 SAM 边界细化。**三件都只在
`--sam` / 默认路径里跑，判据全部来自实测** —— 下面每一条都附读数，改过就重跑。

python tools/ir_contour_seg.py --bitmap <png> --ir <IR> --outdir <dir> --sam    # 再接 SAM 边界细化

### 双引擎：为什么是「旧的不合格才换」，不是「新的更好就换」

| 图 | 老引擎（landmarks：红蓝共现 / 暖橙 / 深色实体） | 新引擎（IR `material` 颜色模型） |
|---|---|---|
| UPC `cand_s4192.png`（2324x1268） | **10/10 全对** | 6/10，N1 40248 px IoU **0.002**、S1/B1/T1/L1 全丢 |
| 喷注淬火 `jet_q_final_2x.png`（3328x1818） | 7/12（B1 认成 421901 px 橙色火球） | **8/9 认对** |

**结论**：颜色语义显式化只在「位图听了 IR」时有效。UPC 位图与 IR 偏差极大（§2.5 那张 LabΔ 表，
N1 57.1），颜色锚点指不到位图的正确区域；老引擎的形状种子恰好对得上。所以仲裁的**方向**是
「老的不合格才换」，反了就会在 UPC 上把 10/10 打成 6/10。

`HARD_GATE` 标定（读数来自 `_mat_t/probe_feats.py`，工作区）：

| 图 | 元素 | 老引擎实测 | 过门？ |
|---|---|---|---|
| UPC | N1 cluster | a%6.489 aspect1.11 elong1.21 sol0.93 | 过 |
| UPC | A1 arrow | a%2.827 elong27.73 sol1.50 | 过 |
| UPC | V1 glow | a%0.296 chroma19.07 elong1.10 sol0.50 **L0.801** | 过（见下） |
| 喷注 | N1 cluster | elong **9.78**（细长碎片） | ✗ 换新引擎 |
| 喷注 | N2 cluster | a% **0.009**（太小） | ✗ 换新引擎 |
| 喷注 | G1 stroke | a% **8.451** thickrel0.14（吞掉整个场景） | ✗ 换新引擎 |
| 喷注 | B1 arrow | sol0.49 elong7.17 | ✗ 换新引擎 |

★ **两条出过回归的坑**（都别再踩）：

1. **glow 不能用绝对亮度**：UPC 顶点画在浅灰板上，老掩膜（顶点+光晕）L=0.801 反而**低于板面**
   L≈0.85 → `L>=0.88` 会把对的判失败，换成 159 px 的亮核碎块（实测回归）。
2. **glow 不能用实心度**：喷注图顶点是**星芒**（短射线放射），sol=0.23 天生低 → `sol>=0.35` 会把
   5796 px 的正确候选判失败（实测回归，V1 整块消失）。
   定稿：`area<=1% ∧ aspect<=3 ∧ elong<=3 ∧ (chroma>=12 ∨ L>=0.88)`。

### SAM：位置是「边界细化提议器」，不是主判据

点提示（正点 = 掩膜内最远点采样 5 个；负点 = 外环带 3 个），只在 IR 定好语义之后修边：

- 3 个候选里取「与现掩膜 IoU 最大、面积在 [0.5,3] 倍内」的；`IoU < 0.25` 报读数跳过。
- 结果 = **有界并集** `new = m | (sam & dilate(m, 0.02·短边))`：绝不整块替换、绝不删像素。
- **细尖刺拦截**：新增块厚度 ≥ 10% 本体最厚处（下限 2 px）。实测喷注图里 SAM 会把「束流箭头尖 +
  板边细线」并进核子并占到可见轮廓上，这条截掉 945 px（V1）/ 428（B1）/ 422（T1）。

读数（对 trace 参考，可见轮廓 IoU，`--sam` 前 → 后）：

| 图 | 元素 | 前 | 后 | SAM 新增 |
|---|---|---|---|---|
| 喷注 | N1 | 0.624 | **0.678** | +11256 px（另有细尖刺被截） |
| 喷注 | N2 | 0.575 | **0.608** | +7410 px |
| 喷注 | V1（星芒） | 0.509 | **0.622** | +2042 px（截掉 945 px 刺） |
| 喷注 | M1（火球） | 0.670 | 0.672 | 0（SAM 候选与原掩膜一致） |
| 喷注 | P1（板） | 0.547 | 0.551 | 0（候选面积出 [0.5,3] 倍，跳过） |
| 喷注 | J1 | 0.557 | 0.535 | +1535 px（把火球内侧弥散边也加了，略稀释） |
| UPC | 全 10 项 | 1.000 | 0.972~1.000 | 只动 P1/A1 边界，合计认领像素 **±0** |

⇒ 喷注图净收益（7 个元素得到更好的边界）；UPC 因为参考就是人工认可的 v4.17c 成品，
SAM 的收益体现为「不破坏」：板亮角修复（S1 = 708149 px）原样保留。

### 球团纹理源的亮度下界 `CLU_L_LO`

核子簇的**暗侧腿**（被遮挡那一侧）原来被 `L > 0.40` 整块排除。实测对 trace 参考：
0.40 → N1 覆盖 0.766 / N2 0.633；**0.22 → N1 0.800 / N2 0.678**，纯度不降。

### 两个还没解决的缺口

- **与板同色系的细长元素会锁错**（喷注图 J2 被淬火喷注：拿到 1821 px 碎块，参考 122920 px，
  覆盖/纯度 0.000）。根因是它和板连成同一个连通域（灰池 12.75% 里 12.078% 是「板+核」巨块），
  不是候选排序问题。已证无效：edge-cut / 抽壳 / 亮度分位。
- **核子簇的细尾**（板边 + 接触阴影）。形态学裁剪不是对的工具：`rel` 0.06→0.15 只是拿覆盖换纯度

### 已知边界（这一版还没做）

- **没有遮挡补全**：完全被挡住的元素拿不到轮廓（只出「缺了多少」的读数）。补全走 §6。

- 文字层的字间距 / 字形不重建，只按连通块成层（§3 之后仍按碎矩形贴回）。
- 位图色与 IR 差得远时，得靠人看一眼 `labels.png` 确认没有整块张冠李戴。

## 2.7 ★ 工作分辨率 `--W`：整条链唯一会「永久丢细节」的旋钮（v4.19）

`scripts/raster_to_vector_semantic.py` 的 `--W` 是 ② 临摹的**工作分辨率宽度**。
它做的事情是：**先把源位图缩放到 `--W` 宽，再在缩放后的图上临摹。**
所以 `--W` 比源位图窄 = 先把图降采样一遍再临摹 —— 细节在这一步就没了，
后面 ③ 无论多精细都救不回来。

- **默认值 = 0 = 取源位图宽（1:1）**（v4.19 起；以前写死 1200）。
  ★ 改 `--W` 的同时必须核对 panels 表的画布（见下）。
  不给 `--W` 时会打印 `工作分辨率 --W 未给 -> 取源位图宽 N（1:1）`。
- 显式给的 `--W` **小于**源位图宽 → 打硬警告（v4.19）。真要小图，
  把理由写进交付说明。

### 读数（UPC，源 `fig_upc_v415/render/pick/cand_s4192.png` 2324×1268；都回渲染到 2324×1268 再比）

| 装配时的 `--W` | MAE | >8 | >32 | PSNR |
|---|---|---|---|---|
| 1664 | **3.022** | 7.38% | 1.98% | — |
| **2324（1:1）** | **1.954** | 2.93% | **0.67%** | 31.51 dB |

肉眼版：`_mat_t/_crop_nucleus.png`（`@W=1664` 核子球糊成一片、`@W=2324` 每个球剪影都在）、
`_mat_t/_crop_boardcorner.png`（`@W=1664` 板面细格线断掉）。

### ★★ `--W` 必须和 **panels 表的画布** 一致（只改 `--W` 不够）

`panels.py` 的 `CELLS` / `ELEMENTS[].boxes` 写在**工作分辨率坐标**里，`groupvec` 不会替你缩放。
实测（喷注淬火，源 1664×928，`panels_jetq.py` 表头 "Canvas = working resolution 1200 x 669"）：

| 跑法 | 回渲染对源 |
|---|---|
| `--W 1664` + 旧 1200×669 表 | 图形只占左上 **72%** → MAE **7.217** / >32 5.03%（比不改还糟！） |
| `--W 1664` + 重标定表 `panels_jetq_w1664.py` | MAE **2.323** / >32 **1.57%** / PSNR 27.55 dB ✅ |
| 旧 `out/jetq_final.svg`（`--W` 缺省=1200） | MAE **3.665** / >32 **3.17%** |

症状识别：回渲染后**内容只占画布一角**、题注/元素全挤在左上 → 就是 `--W` 与表画布不一致
（比例 ≈ 旧表宽 / 新 `--W`）。改法：把表里所有 4-int rect 按 `--W/旧画布宽`、`H/旧画布高` 缩放。

**唯一天然免疫的做法**：语义层走 `--elmap-in`（IR 引导的 `ir_contour_seg.py` 产物），
表里只留 `CELLS` 面板框 + `ELEMENTS` 输出顺序 —— 见
`fig_upc_v415/vec/panels_upc_ir.py`。它的 `CELLS` rect 直接写源图尺寸，所以能随便提 `--W`。

### ★ 别拿 SVG 的 `width` / `viewBox` 当分辨率

v4.14 那条线交付过 `fig_jet_3d/out/jet_q_final.svg`（4992×2727，36.4 MB），
它的「3x 工作空间」是把源位图**插值放大**出来的：

| 文件 | 与源的关系 | 读数 |
|---|---|---|
| `gen/chosen_x2.png`（3328×1818） | LANCZOS 放大 `gen/chosen.png`（1664×909） | MAE **0.000** |
| `gen/chosen_x3.png`（4992×2727） | 同上 | 3× 子采样后 MAE **0.000** |

信息量 = 1664×909（高频梯度 1x 1.786 → 3x 0.627，比值 0.351 ≈ 被插值抹平），
放大的只是容器与坐标网格。**「分辨率高不高」看「源位图宽 × `--W`」，不看容器。**

### 同尺寸同源对账：新路线 vs 旧路线（两者都是 1:1，可比）

## 3. ③-A 对象档：每个元素重做成三件东西

| # | 产出 | 干什么 |
|---|---|---|
| **(a)** | `clipPath` | 该元素在临摹图里的**精确可见轮廓** —— 含**被其它元素遮挡后**的形状（"临摹"相对"重画"最大的优势：位图里的遮挡关系免费） |
| **(b)** | 真渐变 | 颜色场从原图拟合；掩膜先按内缩量腐蚀、再按 σ 平滑，纵向再做一次高斯平滑消掉带间噪声 |
| **(c)** | 线稿逐像素保留 | 网格解释不了的描边 / 切割线 / **穿过球面的格线**，原样照抄 |

判"哪些碎矩形要留"用**残差**：`dev = |模型 − 原图|`，渐变铺不出来的那部分像素，线稿一律留下。
其余元素（板、三轴、文字、箭头、虚线、别的面板）**整段照抄**临摹图。

## 4. ③-B 光滑档（默认交付）：逐行自适应渐变网格（`scripts/shade_smooth.py`）

- 每个元素一条 `clipPath`（几何仍来自 ②）；
- 网格 = 每 `BAND` 像素一条 `linearGradient`（`NSTOP` 个 stop）+ 纵向 `mask`；
- **不引 SVG 滤镜**（`feGaussianBlur` / `feDropShadow` 都不许）—— 引了 PDF 就不是纯矢量、文字也提不出来。

### 判据：`smooth_metric.py`（"放大会不会看出台阶"是可测的）

只在**位图本身就是平滑**的像素上量（相邻步长 ≤ 3，且行、列两个方向都满足），再内缩 7 px；
量 A 与 B 的**相邻像素最大通道差**。实测（喷注淬火 1× 位图，火球面 40662 px）：

| 输入 | mean \|d\| | p99 | **>8 占比** | max |
|---|---|---|---|---|
| 位图自己（对照，测的是它自己的相邻步长） | 1.21 | 3 | 0.000 | 3 |
| **本 skill 光滑档** | **1.19** | **3** | **0.000** | 4 |
| VTracer 0.6.15（默认参数） | 43.67 | 84 | **0.990** | 88 |

**`shade_smooth.py` 回归基线**（喷注淬火 `chosen_x2.png` + `jet_q_trace.svg`，3328×1818，
同一把尺子、同一火球 ROI，64560 px）：本脚本 **mean 1.16 / p99 3 / >8 0.000**，
已交付的 `jet_q_mesh.svg` **1.16 / 3 / 0.000**，位图自己 **1.19 / 3 / 0.000** —— 三者等价。
（本脚本成品 20.3 MB，交付件 34.6 MB。）

⇒ 光滑档在这块区域上与**位图自己的读数无法区分**（1.19 vs 1.21）；VTracer 把柔渐变压成了平色块。
（VTracer 的绝对值随它的旋钮变：`color_precision` / `layer_difference` 调细后会好看很多 ——
**要对照就同一区域、同一批参数比**，别跨配置比数字。）

### ★★ 环境事实：**cairosvg 不画 `<mask>`**

光滑档带 `mask`。用 cairosvg 渲染会**把旁衬层整块丢掉**，于是"成品 vs 位图"的 MAE 全错。

看到"明明写了却像没生效"时，先怀疑渲染器，不要怀疑 SVG。

## 5. ④ 拾取层：「点一下 = 一个物理结构」

### 为什么需要

③ 的成品内部是**几百到几万条 `<path>`**（碎矩形 / 逐行渐变带）。一次点击命中的是**那一条 path**，
不是物理对象 —— 于是"点一下球，选中的是一段渐变带"。

### 做法（`scripts/pick_layer.py`）

- 在 `<svg>` 最后面加 `<g id="pick">`，里面每个物理结构一条**闭合路径**，
  `fill-opacity="0" pointer-events="all"`：**什么都不画，但接管点击**；
- ★ **一次点击由最后画的那条路径决定** ⇒ 顺序必须 = 图里的**真实遮挡**（back → front）。
  `pick_verify.py` 的探针表就是拿来验这件事的；
- ★ **子物体**：`--sub` 传 `{"element": {"paths": [...]}}`（如两个 Pb 核里逐核子一条路径）。
  子路径画在**父级之后** ⇒ 点球选球、点没被切开的区域选核。位图把背排的球画在一起、没给边界时，
  **父级就是兜底**，保证不存在"点不到"的地方。

### 验收（`scripts/pick_verify.py`，三张表）

```
element          pick px  layer px covered  extra   empty   unc smooth unc text
plate            2160131   1168017 0.892    0.518   0.004   0.61      0.39
nucleus-A         138243    192221 0.608    0.155   0.039   0.18      0.82
fireball          659903    475576 1.000    0.279   0.000   0.12      0.88
axes                9487      9430 0.960    0.046   0.046   0.00      1.00
```

- `covered` = 这个结构的可见像素里有多少能点到它自己；
- `extra` = 拾取区里是**补出来的**（被遮住）那一份；
- `empty` = 点在"图里什么都没有"的地方（越低越好）；
- `unc smooth / text` = 没被覆盖的那部分层，到底是**落影/柔边**还是**纹理/格线** ——
  **这一列才是判"该不该再补"的依据**。例：`nucleus-A` 的 `covered` 只有 0.608，
  但那 39% 里 82% 是**纹理**（核投在板上的影子 + 板的暗边带被临摹层算进了核），**不是漏球**。
- 探针表：每个元素取「可见体」「被遮住处」各一点，实测**位图上是甚么 vs 点一下选中甚么**；
  `probes that do NOT do what is claimed = 0` 才算过。有意为之的例外写进 `--expect`。

## 6. amodal 补全：声明式策略（本法的关键一步）

**为什么必须补**：位图只画了**可见**的部分。"点一下 = 一个物理结构"要求选中的是**完整**的物体。
补全 = 把被遮住 / 被抗锯齿吃掉的那一块按**声明的策略**补回来。

策略**只能按 IR 角色声明**（不许用数值判据自动挑，见 §7），每条都要有实测读数：

| 策略 | 用在什么 | 怎么算 | 实测读数 |
|---|---|---|---|
| `none` | 碎笔画（喷注条 / 星芒 / 三轴） | 不补，就是可见轮廓 | —— |
| `hull` | 一个凸体积（热芯 / 束流箭头） | 最大连通域的凸包 | 束流箭头 25658 → 43449 px（补回被球挡住的那一截） |
| `union_close` | **QGP 火球** | 50% 覆盖颜色门 → `open(12)` → `close(20)` → ∪层 → `fill_holes` → `hull` | **659736 px**（位图化 658519，**0.998**） |
| `ballfield` | **Pb 核（球簇）** | 带通纹理超水平集（**不做凸包**）→ `open(41)` → `close(31)` → `fill_holes` → 与层重叠最大的连通域；再**逐核子 watershed** | 核 A **19** 条（16 单球 + 3 合并块）/ 核 B **18** 条；拾取区 138243 / 125234 px |
| `edgequad` | 板（一个平面） | 在位图上**量** 4 条边（沿 4 个方向扫边界跑长）→ 求交得 4 个角 | 远角 `(2045.7, 228.5)`；补回 992441 px |
| `cyan` | 青色逃逸喷注 | 颜色门 → `fill`（**不 hull**：要保住箭头的凹口） | 40207 → 40432 px |
| `skip` | 残差类（辉光 + 弧线 + 抗锯齿边） | 不是结构，不进拾取层 | —— |

### ★ 带通纹理（`ballfield` 的核心，为什么必须带通）

判"哪里是球簇"不能直接用窗口 sd：核投在板上的**落影** sd 实测 **7.8**，`sd>5` 会把影子一起吞进来
（多 23 kpx，ymax 1326 vs 球堆 1193）。**先减掉大尺度亮度起伏再做局部 sd**（带通）就分开了：

| 区域 | 带通后的读数 |
|---|---|
| 球堆 | 中位 **15.3**（p10/p50/p90 = 6.1 / 15.9 / 29.8） |
| 核 A / 核 B 的落影 | **2.2 / 1.3** |
| 空板 | **0.7** |

### ★ 逐核子切分

`watershed(亮度, markers)`，markers = 亮度高光峰（`maximum_filter` + 距离变换门）。
旋钮实测扫描：`sep 0.85r + gate 0.35r` → 核 A/B 各 **21** 个种子；`sep 1.05r + gate 0.50r` → 19/17（会漏背排球）。
**背排的球是位图自己就画在一起的**（没给边界），合并块由**父级兜底**，不是 bug。

## 7. 被废弃的方法（留痕：它们是**错的**，不是"不够好"）

| 判据 / 方法 | 结论 |
|---|---|
| **颜色阈值 ∩ 包围盒**重抠几何 | 底边被切平 / 细带飘带（§2 实测） |
| `fill = visible / hull >= 0.55` 判"够不够凸" | **错**：把「被遮挡形成的洞」算成「非凸」，于是把整块**板**和 `nucleus-A` 一起误拒 |
| `hull & ~mask & ~others` 自动挑补全方式 | 板 0.103 / 核B 0.101 偏高 —— 追下去发现**层的 hull 本身就是错的**（核B 的 hull 把右侧空白月牙包了进来）⇒ **本图上任何"自动挑补全方式"的数值判据都不可用**，只能声明 + 逐条实测 |
| 21 px 窗口 `sd > 5` 找球簇 | **被落影骗过**（落影 sd 7.8）⇒ 必须**带通**（§6） |
| 任何形式的**凸包**用于球堆 | 一定跨过整堆 ⇒ 把 Pb 箭头头和一片空板圈进来（xmin 449 vs 球的 531） |
| 椭圆「读图」补全核（目测圆心/半径） | 盖住整个核、漏 37% 层 ⇒ 点球选中核 |
| `hull(layer)` 补全火球 | 内凹缺口，且 3 个方向上比可见橙边**小 4–30 px** |
| 火球补全**不做 `close`** | 橙色门被灰色喷注条切成 2 块 + 掐点 ⇒ 交付路径只剩 **328419 / 521801 px** |
| **整幅 MAE** 当选型判据 | obj4 反例：MAE 更低，但把三轴吃成了渐变（§3） |
| 用 `cairosvg` 渲染带 `mask` 的成品 | 旁衬层整块丢（§4） |

## 8. 与开源 / 商业工具的差别（数出来的，不是印象）

| | 语义从哪来 | 有没有**补全** | 有没有真渐变 | 能不能"点一下 = 一个物体" |
|---|---|---|---|---|
| VTracer / potrace | **无**（颜色量化 + 轮廓拟合） | 无 | 无（只能平色块） | ❌（0 个 `data-element`） |
| Vectorizer.AI | **无**（"shape" = 几何图元，"layer" = **按颜色**分层） | 无 | —— | ❌（按颜色，不按物体） |
| AmodalSVG / LayerSVG / SAMVG | VLM / SAM 从像素**推断** | 有 | 有 | ✅ |
| **本 skill** | **IR 里人工声明的物理角色** + 逐条实测 | 有（声明式策略，§6） | 有 | ✅ |

⇒ 「语义分割」这个动作在前两行**根本没有**，在第三、四行**都有**，区别在**语义的来源**：
它们是模型推断，我们是**可审计的声明**。

★ 2026-10-15 补（实测，见 §2.5 实测三）：第三行的「SAM 从像素推断」现在有读数了 ——
在同一张 UPC 位图上，SAM 对**最大的物理元素**（反应平面，占画布 20.3%）**98% 的像素拿不出任何块**；
同一张图只换一组阈值，核 N1 的最大块就从 1% 跳到 90%。
所以「它们靠模型推断」这句话，问题不只是「不可审计」，而是**在同一张图上就不稳定**。

## 9. 逐字可跑（以喷注淬火图为例）

```bash
# ① 位图（客户选定）
#     fig_jet_3d/gen/chosen_x2.png   3328x1818

# ② 临摹（几何的唯一来源）
python scripts/raster_to_vector_semantic.py fig_jet_3d/gen/chosen_x2.png \
       -o fig_jet_3d/build/jet_q_trace.svg

# ③-A 对象档（可改形状）
python build/objfit3.py --klayers 12 --nstops 16 \
       --sil build/mesh/_sil.json --out out/jet_q_obj.svg

# ③-B 光滑档（默认交付）—— 逐行渐变网格 + 纵向 mask，一条命令（几何仍只从临摹层来）
python scripts/shade_smooth.py --src gen/chosen_x2.png \
       --trace <第②步的临摹.svg> --stem jet_q --outdir out --size 3328x1818
#     回渲染用 Edge / Chrome（带 <mask>，cairosvg 会丢旁衬层）；判据见 smooth_metric.py

# ④ 拾取层 + 验收
python scripts/pick_layer.py out/jet_q_mesh.svg \
       --sil build/mesh/_sil.json --sub build/mesh/_nuc_balls.json \
       -o out/jet_q_mesh_pick.svg
python scripts/pick_verify.py --sil build/mesh/_sil.json --vis build/mesh/_vis_trace.npz \
       --ref gen/chosen_x2.png --size 3328x1818 --outdir out --stem jet_q \
       --expect '{"fireball-core":"fireball"}' \
       --nuc-balls build/mesh/_nuc_balls.json --json build/_pick_coverage.json

# 光滑判据
python scripts/smooth_metric.py gen/chosen_x2.png out/jet_q_mesh_render.png \
       --mask build/mesh/_vis_trace.npz:fireball

# 闸门（缺一不可）
python scripts/axis_gate.py --svg out/jet_q_obj.svg --png gen/chosen.png --ir ir/*.ir.yaml
python scripts/check_3d_generic.py gen/chosen.png --ir ir/*.ir.yaml
python scripts/check_render_mode.py out/jet_q_obj.svg
```

★ **`_sil.json` 是 ③ 与 ④ 之间的接口**：`{"element": "<path d>", ...}`，顺序 = back → front。
子物体另出一份 `_nuc_balls.json`。这两份文件就是「按物理结构」的全部秘密。
